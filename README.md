# erp-query-mcp

An [MCP](https://modelcontextprotocol.io) server that lets an LLM answer questions
about an ERP database in plain English:

> Which parts are below their reorder point?
> How many invoices are unpaid, and what is the total outstanding?

The model writes the SQL. The server's job is to make sure that whatever it writes
can only read.

Three tools: `list_tables` (tables and row counts), `describe_table` (columns,
types, keys), `run_query` (one validated SELECT, capped at 200 rows). Schema
discovery matters more than the query tool — a model that cannot see the schema
writes plausible SQL against columns that do not exist.

The database here is synthetic, generated by `scripts/seed.js`: a mid-size
manufacturer, ~400 orders over six months, seeded deterministically.

## Guardrails, and how much each one is worth

Two layers, and they are not equal:

**The read-only connection is the real one.** SQLite is opened with
`readOnly: true`, so the database itself rejects a write. Nothing the model
produces can get past that.

**The keyword denylist is coarse, and I would not rely on it.** `validateQuery`
rejects multiple statements, anything not starting with SELECT or WITH, and a
list of mutating keywords. It scans rather than parses, so it over-rejects: a
manufacturer stocks threaded inserts, and

```sql
SELECT * FROM parts WHERE description LIKE '%INSERT%'
```

is a plain read that the denylist refuses. So is a vendor search for a company
named Grant. Both are pinned in `test/validation-limits.test.js` as known
behavior, along with the identifiers it correctly does *not* trip on
(`update_date` is safe — underscore is a word character, so the word-boundary
match never fires).

Over-rejection is the right direction for this layer to fail in: the model gets
a clear reason and rephrases, so the cost is a retry rather than a wrong answer.
Fixing it properly means parsing the statement instead of scanning it, which is
worth doing only if the false positives turn out to matter. If I removed a layer
it would be this one — and if I removed the read-only flag instead, the denylist
would not save me.

Row caps are the third thing, and they are about cost and context, not safety: an
unbounded result set from a model that wrote `SELECT * FROM invoices` will fill a
context window and accomplish nothing.

## The production version did the opposite, on purpose

I built a version of this against a real manufacturing ERP during an internship.
That one has **no free-form SQL surface at all**. Every tool maps to one
hand-written SELECT — revenue for a period, top customers, open orders, AR aging,
work orders at risk. It is read-only by construction: there is no code path that
writes and no place to inject.

The trade is real. A fixed menu cannot answer a question nobody anticipated, and
every new question costs a code change. Free-form SQL answers anything and puts
you in the business of proving a validator is airtight. Against a production
database with a finance team downstream, I did not want to be in that business —
and the questions that actually got asked were a small, stable set worth writing
by hand.

This repo is the free-form design, which is the more interesting one to reason
about and the one worth having runnable. It contains none of that code and none
of that data.

## Run it

```bash
npm install
npm run seed     # creates data/erp-demo.db
npm test
```

Claude Desktop (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "erp-query": {
      "command": "node",
      "args": ["/absolute/path/to/erp-query-mcp/src/index.js"]
    }
  }
}
```

## What is missing before this is production-shaped

Auth, query logging, per-caller result budgets, and a timeout on the query itself
— a model can write a cartesian join as easily as a good query. None are here.

Node.js >= 22.5, `@modelcontextprotocol/sdk`, `node:sqlite`, zod, `node:test`. MIT.
